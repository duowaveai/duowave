# DuoWave: архитектура

Сервис говорит с Яндекс Станцией на её собственном голосовом протоколе (uniproxy) и
направляет речь в наши распознавание, LLM и синтез. Это своя реализация, а не перенос чужого
кода: протокол описан по наблюдаемому поведению колонки и минимальной схеме полей
(`gateway/proto/station-protocol.proto`), которая нужна для совместимости.

Шлюз — крейт `gateway/` на Rust (пакет и программа `duowave`, [README](../gateway/README.md)). С 06.11.2026 он
заменил шлюз на Node/NestJS: тот удалён из дерева и остался в истории git под тегом `node-gateway-last`, а дерево
модулей крейта повторяет его `src/` в snake_case (правила — [gateway/PORTING.md](../gateway/PORTING.md), ход
переноса — план). Пути `src/…` ниже — от `gateway/`.

## Как колонка попадает на сервер

Режим по умолчанию — **гибрид**: на колонке с root в `/system/vendor/quasar/quasar.cfg`
`aliced.uniProxyUrl` указывает на `ws://<сервер>:<порт>/uni.ws`, `aliced.uniProxyQuicUrl`
пустой. Активация, аккаунт и онлайн-конфиг остаются у Яндекса; к нам приходит только
голосовое соединение. Онлайн-конфиг Яндекса `uniProxyUrl` не перезаписывает (проверено
31.10.2026).

Голос Алисы для ответов шлюз берёт у Яндекса сам, через свою сессию, открытую учётными
данными колонки (см. «Ответ»). Как закрыть колонке прямой выход в Яндекс — в
плане.

Любые действия на колонке — только с согласия её владельца: сначала копия того, что меняется, и известный способ отката.

## Слои

| Слой | Что | Где (`gateway/src/`) |
|---|---|---|
| transport | WebSocket на axum, путь /uni.ws, одна сессия на соединение | `gateway/uniproxy/uniproxy_server.rs` |
| protocol | кадры: AAPI-protobuf \| поток звука `[u32 BE streamId][Ogg]`; кодек ↔ внутренняя модель | `gateway/protocol/` |
| session | состояние соединения, потоки, запросы (`VoiceRequest`), порядок отправки, отмена; живые сессии; режимы | `gateway/uniproxy/` (`station_session.rs`, `voice_request.rs`, `session_registry.rs`), `gateway/mode/` |
| speech | Ogg/Opus, VAD, конец фразы, распознавание, свой синтез; склейка фраз ответа в один поток Ogg | `speech/`, `gateway/uniproxy/spoken_answer.rs` |
| dialog | LLM со стримингом по фразам, инструменты, профили моделей, «Мозг», характер, история по устройству | `dialog/` |
| skills | каталог возможностей, маршруты (own/yandex/off), быстрые правила, наши реализации | `skills/` |
| yandex | одна сессия uniproxy на колонку с её учётными данными: синтез, push, маршрут «Яндекс»; ретрансляция | `gateway/yandex/`, `gateway/uniproxy/` (`yandex_relay.rs`, `relay_session.rs`) |
| media | /media и свой audio_play: радио, музыка, сказки | `gateway/media/`, `skills/media/` |
| calls | узел звонков: WebRTC-страница, клиент колонки по HTTP, переходники LiveKit, SIP и Telegram | `calls/` (только сборка для ПК) |
| operations | домашние сети (доступ к отладке), срок хранения журналов, присмотр за колонкой и оповещения | `operations/` |
| placement | где работает шлюз: что где доступно, состояние шлюза, файлы и команды колонки, сборка колонки внутри компьютерной, пара, пакет настроек и копии, переходы | `core/availability.rs`, `placement/` |
| home server | домашний сервер колонки: `/home/v1` на компьютере, коннектор и порядок «компьютер → облако → Яндекс» на колонке | `home_server/` |
| observability | журнал событий, запись звука, таймлайны запроса и ответа, отладочный API | `gateway/observability/`, `gateway/debug/` |

Внутренняя модель (`src/gateway/protocol/protocol_types.rs`) — свои типы событий, не JSON-формат старых
прошивок. Кодек (`aapi_codec.rs`) переводит провод в модель и обратно; сессия не знает про protobuf. Типы
провода (`pb`) собираются из `gateway/proto/station-protocol.proto` при сборке (`gateway/build.rs`, protox и
prost, без protoc).

## Платформа: люди, права, настройки, подключения

Поверх голосового тракта — платформа, на которой растут семья, подключения и сценарии
([ROADMAP.md](../ROADMAP.md), этапы 2–4). Правило одно: новое добавляется в своё место, ядро
не меняется.

```
gateway/src/

lib.rs       модули крейта и журнал (tracing; RUST_LOG)
app.rs       сборка шлюза: сервисы по порядку (конфигурация, база, события, секреты, настройки, доступ, затем
             функции), связи между ними и все маршруты HTTP (router)
config/      переменные окружения и .env (DATA_DIR/.env, затем ./.env) в типизированные разделы; DATA_DIR
core/        чистые типы и правила, без ввода-вывода — их же возьмёт облачная часть
  identity/    права (permissions.rs), роли (roles.rs), участник (principal.rs), политика can() (policy.rs)
  events.rs    типизированная шина событий (EventBus): аудит, живой канал пульта, будущие сценарии
  settings.rs  объявление настройки (SettingDefinition): ключ, чья она (общая или человека), как читать сохранённое
  connectors.rs  манифест подключения, его состояние, инструменты для модели, реестр
  requests.rs  запрос как путь: шаги (слух, распознавание, мозг, справка, голос), кто их делал, итог
  stations/    присутствие колонки: по каким её каналам и в каком она состоянии
platform/http/  обёртка ответов и ошибки (api.rs), кто и откуда спрашивает (caller.rs, zone.rs), заголовки защиты
             и проверка Host (security.rs)

             состояние устройств (state.rs)

             подключение колонки из пульта (connect/: скрипты для ручного подключения — в любой сборке,

connectors/  встроенные подключения: Яндекс, модель, распознавание, голос, Home Assistant, Telegram…;
             settings.rs — настройки подключений из пульта, checks.rs — «Проверить», controller.rs — их API
health_status/  /health: версия и возможности сборки, колонка, распознавание, маршруты, счётчики
updates/     лента выпусков, подпись minisign, предложение и установка обновлений
links/       связи между модулями: каждый модуль объявляет маленький трейт того, что ему нужно от другого,
             здесь он реализован поверх настоящего сервиса и передан в App::build
```

Сервисы — структуры, собранные со своими зависимостями (`Arc<Db>`, `EventBus`, `Arc<SettingsService>`…) и
хранимые в `App` за `Arc`. Где в Nest был цикл зависимостей, в Rust — события шины или поздняя ссылка
(`OnceLock`).

**Доступ.** Каждый HTTP-маршрут закрыт, если сам не сказал иначе: обработчик берёт `Caller`
(`src/platform/http/caller.rs`) и спрашивает его в порядке прежнего `AccessGuard` Node-шлюза.
`caller.zone_at_least(Zone::Home)?` сужает «откуда»: домашние сети из `DEBUG_API_ALLOW` и этот компьютер,
никогда — туннель. `caller.signed_in()?` требует вошедшего человека или ключ,
`caller.permitted(permissions::MODELS_MANAGE)?` называет право. Публичный маршрут не спрашивает ничего. Снаружи дома (туннель, открытый порт) всё, что требует
входа, отвечает только с `PANEL_REMOTE=true`. Права проверяет одна функция `can()` — для пульта, для ключей
скриптов и агентов, для голоса и для инструментов модели.

**Люди.** Роли — администратор, домашний, гость (`src/core/identity/roles.rs`); поверх роли администратор
даёт человеку `allow` и `deny` (например, ребёнку — `deny: use:calls`). Человек без пароля — профиль,
который колонка будет узнавать, а не учётная запись пульта. Смена пароля, роли или статуса
увеличивает `token_version`: все сессии человека заканчиваются. Последнего администратора нельзя
понизить или удалить. Первая настройка — только из дома; не с этого компьютера — с кодом из журнала
шлюза.

**Голос.** У каждого голосового запроса есть участник (`Principal`): пока это «голос дома» —
роль и ограничения, которые задал администратор (`HouseholdService`, по умолчанию домашний).
Маршрутизатор не отдаёт возможность, на которую нет права (`use:<возможность>`), и колонка
говорит «не разрешено», а не «не умею»; модели предлагаются только разрешённые инструменты.
Узнавание по имени или по голосу подставит в `speaker()` конкретного человека — остальное уже работает.

**Режим.** Яндекс / Шлюз / Свой — `ModeService`, единственный источник правды. «Свой» — наложение,
а не переписывание маршрутов: сессия с Яндексом не открывается, шаги `yandex` пропускаются, голос
Алисы уступает нашему; маршруты остаются предпочтением дома и работают как есть в «Шлюзе». Чей голос
отвечает — `VoiceService`: конфиг больше никто не правит на лету.

**Настройки.** Все ключи — в `src/settings/definitions.rs` (`SettingDefinition`): общие и «на человека»
(свой характер или голос поверх общего). Запись публикует `settings.changed`; кто хранит копию в
памяти (маршруты в `SkillsService`), перечитывает её по событию.

**Колонки.** Голосовой сокет колонки не умеет входить, поэтому колонку сначала разрешают
(`StationsService`): первая доверена при первом подключении, каждая следующая ждёт администратора, а
владельцу приходит оповещение. Браузер не может прислать заголовок устройства колонки, поэтому
страница из интернета колонкой не притворится. Служебные адреса колонки (клиент звонков, мост
микрофона) верят только адресу одобренной колонки. `STATION_PAIRING=open` — для тестов и стенда.
При синхронизации колонка называет себя (`device_model` — кодовое имя прошивки) и свой цвет (`device_color`):
шлюз хранит это в её записи (событие `station.synced`). Вид колонки в пульте (`src/stations/looks.rs`) —
семейство, вариант и цвет: что ясно из данных, выбрать нельзя (цвет; вариант, если в таком цвете он
один), остальное выбирает человек (`model`, `color` в `PATCH /api/v1/stations/:device`, пусто — по
умолчанию). Лайт 2 не сообщает, есть ли у неё часы, поэтому синюю, фиолетовую и розовую спрашивают.
Нарисована вся линейка: коды взяты с устройств под рукой (`yandex-station-extended/docs/devices`) и из
списка платформ интеграции YandexStation (облачный device_list) — `plum` Лайт 2, `yandexmicro` Лайт,
`yandexmini`/`yandexmini_2` Мини и Мини 2, `bergamot`/`pickle` Мини 3 и Про, `yandexstation` Станция,
`yandexstation_2` Макс (и ревизия с Zigbee), `yandexmidi` Станция 2 (внутреннее имя Midi — не Миди:
та `cucumber`), `chiron` Дуо Макс, `orion` Станция 3, `mango` Стрит. Код Станции BORK не публиковался —
в таблице догадка `bork`, поправится при первой настоящей синхронизации. Рисунки: корпус каждой модели
по фото Яндекса — `panel/src/stations/models.tsx`; свет Алисы, передний дисплей и анимация общие —
`panel/src/stations/kit.tsx`. Ждёт — свет ровного цвета того, кто отвечает, и дышит; слушает — свет
переливается цветами Алисы, полоски дисплея бегут от краёв к центру; думает — больше фиолетового, в
серединке кольца кружатся цвета; говорит — полоски бегут от центра наружу. У Лайт 2 есть наклейка-котик
(`sticker`). Превью всех моделей и состояний — `panel/src/preview.tsx`, собирается esbuild'ом.

**Присутствие колонки.** На связи ли колонка, шлюз узнаёт без единого запроса к ней — по тому, что
она сама открывает (`PresenceService`, `src/core/stations/presence.rs`): голосовой сокет (события
`station.connected`/`disconnected`), а где на колонке наш клиент (`station-client/`) — мост микрофона
и опрос звонков (`station.channel`, по адресу, с которого приходит её голосовой сокет). Клиенты
поднимаются через секунды после старта шлюза, голосовой сокет колонка открывает по своему расписанию
(от 10 секунд до минут) или сразу по «Алиса» — отсюда «голос ждёт «Алиса»». Пока колонку слышно,
`last_seen` её записи обновляется раз в минуту, в момент потери и при остановке шлюза; после
перезапуска колонка, которую видели перед ним, три минуты «переподключается», а не «не в сети».
Пинг не нужен и не делается: это был бы запрос к колонке.

**Запросы.** Всё, что спросили у колонки (голосом, текстом) или что шлюз сказал сам (напоминание,
«Сказать» из пульта), — запрос (`src/core/requests.rs`): шаги `listen` → `recognize` → `think` →
`tool` → `speak`, у каждого — кто его делал (`own` дома, `cloud`, `yandex`, `agent`) и что именно (модель,
голос, возможность); слова — что услышано, что ответено; итог — `answered`, `silent`, `cancelled`,
`failed`. В «Шлюзе» и «Своём» шаги отмечает сессия (`station_session.rs`: `begin_trip`, `step` у
каждого исполнителя, конец — у ответа или у ретрансляции Яндекса, кто последним взял запрос
(`claim`), тот его и закрывает); ответ кончается, когда колонка договорила (звук уходит быстрее, чем
играет). В «Яндексе» путь читается с кадров, ничего в них не меняя (`relay_trips.rs`): распознавание
Яндекса, его ответ, его поток речи, статистика колонки в конце. `RequestsService` публикует запрос
целиком при каждой перемене (`request.updated`, раз за такт), пишет законченный в таблицу `requests` и
хранит её `requests_keep_days` дней (по умолчанию 30, 0 — не хранить, не больше 20 000 строк); запрос
без конца три минуты закрывается как `failed`. Слова — то, что говорили люди: их видит только право
`journal.view`, остальным — путь без слов. Задел: `kind` — открытый список (сценарий, звонок,
сообщение), `parent` связывает цепочки и шаги сценария, запросов у колонки может идти несколько
сразу, журнал — то, из чего будет учиться домашняя модель.

**Живой канал.** `GET /api/v1/live` (`src/live/`) — Server-Sent Events по обычному GET с тем же входом,
что весь API (пульт читает его fetch'ем: EventSource не умеет заголовок). Сначала `hello` — часы
шлюза, присутствие колонок, идущие и последние запросы; потом `request`, `presence` и `changed` с
именем перемены (режим, маршруты, голос, характер, модели, колонки) — пульт перечитывает своё сразу,
а опрос остаётся страховкой (раз в 15 с вместо 3). Отметка раз в 20 с держит канал через прокси; через
15 минут шлюз закрывает канал, пульт открывает его заново — с новой проверкой входа.

**Дашборд.** Экран «Колонка» в пульте: колонка в центре орбиты, вокруг — мозг и мышление (`brain` в
`/health`: провайдер, модели профилей, `effort`, уходит ли вопрос из дома), характер, слух и голос,
снизу — капсула подключений: спутники в ряд и «Подключено · N». Сцена считается под экран
(`panel/src/screens/dash-scene.ts`): орбита и колонка в ней ужимаются по высоте, что остаётся до панели
вкладок, а подписи и круги узлов не мельчают; на совсем низком экране остаток прокручивается. Логика
узлов отдельно от отрисовки (`panel/src/screens/dash-model.ts`), рисунок — на семейство
(`panel/src/stations/`, те же входы у любой модели). Путь вопроса — настоящий запрос из живого канала
(`panel/src/screens/trip.ts`): шаг запроса — шаг орбиты, цвет кометы и кольца — кто его делает, под
колонкой — что услышано или ответено; итог висит шесть секунд. Без запроса нажатие на колонку
показывает путь на примере. Чего шлюз ещё не умеет (помощники), там показано честно: «скоро»; глубина
мышления модели из `.env` — «задаётся в .env».

**Подключения.** Подключение описывает себя манифестом: что это, уходят ли данные из дома
(`cloud`), где настраивается (`setup`: свой лист в пульте, «Мозг», «Голос», режим), какие возможности
обслуживает; сообщает состояние — работает, настроено, не настроено, выключено, нет связи — и, если умеет, даёт
модели инструменты с правом на каждый (`src/core/connectors.rs`). Реестр показывает их пульту
(`GET /api/v1/connectors`, «Дом» → «Коннекторы»); MCP-серверы добавляются в список сами.

Home Assistant, Telegram, LiveKit, SIP, город погоды и ленты новостей настраиваются в пульте
(`src/connectors/settings.rs`): обычные поля — по настройке на подключение (`connector_*` в
`settings/definitions.rs`), токены, пароли и ключи — в `secrets` (`connector:<id>:…`). `.env` их только сеет:
при старте, когда в базе нет строки подключения, его значения переезжают один раз (с отметкой `is_default` —
«перенесено из .env»), дальше `.env` для него не читается, а очищенное в пульте остаётся очищенным. Модули
берут значения на лету: навыки — при каждом запросе (`SkillConnectors`), MCP — адрес Home Assistant, оповещения
о колонке — свой чат, проверка Host — имена LiveKit; бот и мосты звонков слушают перемены (`CallsConnectors`,
`CallsService::refresh`): тот же бот меняет контакты на месте, другой токен опрашивает с первого своего
обновления, мост SIP или LiveKit заново — завершает свои звонки, отпускает порт RTP и уступает место новому.
«Проверить» (`checks.rs`) спрашивает каждый сервис один раз и отвечает словами, без секретов и адресов с
токенами; итог живёт в памяти как состояние подключения до его перемены. Перемена — событие
`connector.changed` (какие поля, без значений) в журнале изменений и живом канале. Каталог лент
(`skills/lookups/news_catalog.json`) вшит в программу: «новости спорта» читает ленты своей темы.

**Мозг** (`src/dialog/brain/`, `src/dialog/llm/brain.rs`). Модель для ответа берётся у источника мозга по
профилю (быстрая, умная) и держится до конца ответа: смена в пульте действует со следующего вопроса.
`BrainService` — провайдеры из пульта (`llm_providers`, ключи в `secrets`) и выбор `BRAIN`; без выбора —
`EnvBrain` из `.env`. Каждый вызов инструмента получает ответ (лишние — «не выполнено»), ошибка доходит до
модели как ошибка, последний круг оставляет инструменты с `tool_choice: none`, число кругов ограничено и
временем. Неизменная часть промпта (характер и «Подключения») с инструментами кешируется у Claude.

**MCP** (`src/mcp`). Клиент — SDK rmcp за одной прослойкой (`mcp_connection.rs`): программа по stdio (только
в сборке для ПК) или адрес по Streamable HTTP (запасной — старый SSE, `mcp_legacy_sse.rs`), версия договаривается сама
(2026-07-28 — через `server/discover`, старые — `initialize`). `McpService` держит соединения, применяет
доверие (отпечатки инструментов, одобренная инструкция) и выдаёт модели `McpOffer`: инструменты
`mcp_<сервер>__<инструмент>` для говорящего — по праву `mcp.use`, «голосом можно» и маршруту привязанной
возможности. Сессия колонки даёт их в разговоре и в командах (команда, отданная серверу, продолжается
разговором с ранним ответом); после текста из интернета остаются только читающие. Вход в облачные
серверы — OAuth через SDK (`mcp_oauth.rs`), возврат на `localhost/api/v1/mcp/oauth/callback`.

**Секреты** (`src/secrets`). Ключи провайдеров, токены и переменные MCP, токены OAuth и секрет подписи
пульта — в `secrets`, AES-256-GCM, каждый привязан к своему id; ключ шифрования — `<STATE_DIR>/secrets.key`
(0600). База, её журналы и копии — 0600.

- **Сценарии**: триггер — событие шины или фраза (законченный запрос — `request.updated`), шаги —
  инструменты и запросы с `parent`, проверка прав — та же `can()`.
- **Обучение по журналу запросов**: что спрашивали, кто и как ответил — с согласия дома.
- **Агенты** (OpenClaw, Hermes): исполнитель возможностей — шаг маршрута помимо `own` и `yandex`.
- **MCP дальше**: каталог MCP, «спросить голосом» перед инструментом, который меняет данные, навыки
  сервера (`ext/skills`), поиск инструментов на стороне Claude, свои серверы у каждого домашнего.
- **Подключения из пульта дальше**: облачные распознавание и голос (адрес и ключ), вебхук оповещений и порог
  «колонка пропала», новости из Telegram-каналов.
- **Узнавание говорящего**: по обращению («это Аня»), дома — по голосу; `HouseholdService.speaker()`.

## Где работает шлюз (`src/core/availability.rs`, `src/placement/`, `src/home_server/`)

Три размещения (план): на компьютере, на колонке, на колонке с компьютером как
домашним сервером. Сборка для колонки — та же программа без тяжёлых частей (`--features station`); на компьютере
её роль можно сыграть `DUOWAVE_ROLE=station` (так идут сквозные тесты пары).

- **Что где доступно** — один реестр (`core/availability.rs`): у функции пути в порядке предпочтения («здесь», «на
  компьютере», «облако», «Яндекс») и что каждому нужно (сборка ПК, размещение, домашний сервер на связи, облако,
  не «Свой»). `AvailabilityService` (`placement/availability.rs`) применяет его к этому шлюзу:
  `/api/v1/availability`, событие `availability.changed`, переключатель режимов спрашивает его же. Пульт читает
  через `panel/src/availability.ts` (`available`, `whyNot`, `here`); список id для пульта пишут тесты шлюза.
- **Состояние шлюза** — одна запись `gateway_state` в базе: кто выбрал режим (человек или сам шлюз), переход шлюза и
  его причина, страховка и её последний случай, где главные настройки. Чего нет — по умолчанию.
- **Колонка сама по себе** (`placement/station_fs.rs`, `duowave station …`): программа, `.env` и служба
  (`/data/opt/duowave/gateway.sh`), куда идёт голос, страховка службы. Одна реализация для пульта (по SSH), для рук и
  для шлюза на колонке; всё под корнем — тесты идут на папке.
- **Куда идёт голос** (`station-client/voice.sh`, `stations/connect/station_scripts.rs`): файл прошивки `quasar.cfg`
  не меняется никогда. Наша копия с двумя другими адресами лежит в `/data/opt/duowave/voice` и подключается поверх
  него bind-mount'ом только для чтения. При каждой загрузке её подключает `/etc/init.d/S95duowave` (до `S99quasar`) —
  и только поверх того самого файла, с которого она снята, и только с адресом, который записали мы. Отсюда: сброс
  колонки (чистит `/data`) и обновление прошивки (меняет её файл) оставляют обычную Алису. Копия, которую изменил кто-то
  ещё, не переписывается без `--force` и не подключается. Шлюз на колонке выключен страховкой или удалён — копия, что
  ведёт голос к нему, не подключается: голос идёт туда, куда шёл до него (`previous.cfg`), или к прошивке. Проверка
  на настоящем ядре и busybox — `station-client/tests/station-check.sh` (контейнер в CI, эмулятор КУЯСЭ —
  `scripts/emulator`).
- **Сборка колонки внутри компьютерной** (`gateway/build.rs`, `placement/payload.rs`): подписанный архив
  (`DUOWAVE_STATION_PAYLOAD`), иначе файл или лента выпуска этой же версии; подпись проверяется до колонки.
- **Пара**: компьютер ходит в шлюз колонки ключом пары (`PEER_KEY` в `.env` колонки), колонка в компьютер — ключом
  компьютера с правом `home.models`. Компьютер раз в 30 с читает `/health` колонки (`placement/watch.rs`): версия,
  память, место, домашний сервер, голос, ревизия настроек — и сам ведёт синхронизацию: новая ревизия на колонке —
  копия у себя (последние 10, запечатаны ключом пары), настройки на компьютере — отправка колонке.
- **Пакет настроек** (`placement/transfer.rs`): таблицы людей, ключей, характеров, провайдеров, MCP-серверов и
  колонок, настройки и секреты, которые едут, — не файл базы; у каждой стороны остаётся своё (размещение, пара,
  голос из своего каталога). Применяется при старте, до чтения базы службами, с копией базы перед ним.
- **Переходы** (`placement/moves.rs`): задания по SSH, как мастер подключения: на колонку (проверка, путь назад,
  сборка, `duowave station install`, настройки до первого старта, голос, ожидание), на компьютер (настройки с
  колонки, голос сюда, служба колонки — стоп), «Вернуть как было». Тесты гоняют поддельную колонку через её же
  команды.
- **Домашний сервер** (`home_server/`): на компьютере `/home/v1/asr|tts|llm` — свой сервер распознавания, свой
  голос (лаборатории тоже) и своя модель; на колонке коннектор, проверка раз в 15 с, распознавание цепочкой
  «компьютер → облако → Яндекс», голос «компьютер → облако → голос Алисы», модель компьютера — провайдер «Мозга».
  Компьютер пропал на две проверки — «Свой» уступает «Шлюзу» как переход самого шлюза; минуту на связи — возвращается,
  если человек не решил иначе.

## Пакеты и плагины (`src/plugins/`, `packages/`, `panel/src/shell/`)

Новое приходит пакетами, ядро не меняется (план, [как написать плагин](plugins/AUTHORING.md)):
папка `DATA_DIR/packages/<id>/<version>/` с `manifest.json` (`kind`: плагин, приложение, персонаж, тема) и кодом.

- **Хост** (`plugins/controller.rs`): реестр пакетов и включённых (таблицы `packages` и `plugin_kv`), вид пакета
  (системный, встроенный, свой, из каталога); загрузка при первом вызове, выгрузка после простоя, перезагрузка без
  потери прежней версии, откат; `PLUGINS_DISABLED=1` — без плагинов.
- **Движки** за `PluginRuntime`: QuickJS (`rquickjs`, поток на плагин; голос и инструменты ≤ 2 с), WASM (`wasmi`,
  фича `wasm`), MCP-сервер в сети (`mcp_runtime.rs`) и приложения — свои программы под надзором (`src/apps/`:
  хеш сборки, `health`, перезапуск с паузой, память по RSS, Host API по localhost HTTP, свой звук через `/media`).
- **Host API 1.1** с проверкой прав манифеста: фразы и намерения (мост `PluginSkill` → `OwnSkill`, встроенный навык —
  запасной вариант; ответ — речь, `play`, модель шлюза, продолжение разговора), `say`, инструменты «Мозга»
  (`ToolContribution`; ответ `{say, play}` сразу действует), `fetch` к разрешённым хостам, `kv`, настройки,
  события (и плеера), `host.call` — службы шлюза (`links/plugins.rs`: свои папки, инструменты других плагинов,
  умный дом, город погоды, ленты новостей). Управление колонкой плагину не отдаётся.
- **Встроенные плагины** (`plugins/bundled.rs`, `packages/`): вшиты в сборку и раскладываются при старте; радио,
  погода, новости, своя музыка, сказки, игры, утреннее шоу, умный дом. Встроенные навыки остаются запасными, а
  встроенные источники медиа уступают источникам плагинов.
- **Память на колонке** (`plugins/budget.rs`, `operations/system_memory.rs`): бюджет плагинов из живой памяти минус
  запас, у каждого — объявленная доля; под давлением выгрузка, отложенные фоновые вызовы, выключение последнего
  включённого; строки `plugins`, `plugins.apps`, `media.transcode` в реестре «что где доступно».
- **Медиа**: один `MediaSource` для радио, музыки, сказок и источников плагинов; ассеты пакета —
  `/media/packages/<id>/…`, звук приложения — `/media/apps/<id>/…`. Плеер следит за ответами колонки
  (`skills/media/playback.rs`): молчит 5 с — поток идёт через шлюз (`/media/stream/<token>`, AAC → MP3 ffmpeg),
  ответы — в журнал запроса и плагину.
- **Мастерская** (`plugins/workshop/`): черновики `packages-dev`, песочница, агент на «Мозге» со скиллом
  `docs/plugins/skill/`, установка с одобрением администратора, голосовой режим, MCP `/mcp/workshop`, `duowave plugin`.
- **«Колонка + сервер»**: плагин с `prefer: home` зовётся на компьютере по ключу пары (`/home/v1/plugins/…`);
  каталог и архивы колонка берёт через компьютер, если сама не достаёт.
- **API**: `/api/v1/packages` (все виды; включать, выключать, перезагружать, откатывать, копировать —
  `plugins.manage`), `/api/v1/packages/resources`, `/api/v1/packages/themes`, `/api/v1/packages/panel`, события
  `packages.changed`, `plugins.resources`, `workshop.changed`; инструменты плагинов — MCP `/mcp/plugins`
  (`plugins.mcp`). Каталог — подписанная лента (`plugins/catalog.rs`, minisign).
- **Пульт** (`panel/src/shell/`, `panel/src/sdk/`, `panel/src/plugins/loader.ts`): тема — данные (палитры, раскладка,
  плотность, шрифт, скругления), оболочки `TabbarShell` и `SidebarShell`, реестр разделов и слоты с границами
  ошибок; `panel.js` пакетов грузится с шлюза на ходу через import map (её хеш — в CSP), SDK пульта —
  `@duowave/panel-sdk`; `?safe=1` — без плагинов. Контракт темы — `docs/design/glass/THEMES.md`.

## Речь (этап 2, `src/speech/`)

Один `SpeechPipeline` на голосовой запрос; все решения — по времени звука, без таймеров:

```
байты колонки → OggOpusDemuxer (цепочки по OpusHead) → OpusPcmDecoder (16 кГц) → буфер PCM
  до SpotterEnd буфер с «Алисой» держится; на SpotterEnd:
  GainStage: усиление по самому громкому окну «Алисы» (до −20 dBFS, не больше +40 дБ)
  VAD окнами по 32 мс (в т. ч. по буферу — для поиска начала «Алисы»): Silero в сборке с --features silero,
  без неё — по энергии (VAD_ENGINE=energy)
  Endpointer: guard 320 мс → начало речи (96 мс) → конец: 700 мс тишины | нет речи 5 с | 15 с речи
→ звук для распознавания: от начала «Алисы» − 200 мс до конца речи + 200 мс, паузы длиннее
  500 мс сжаты, одно усиление на всю фразу без клиппинга
→ OpenAI-совместимое /audio/transcriptions (GigaAM в asr-server/ или облако)
→ очистка текста: «Алиса» (и до двух слов перед ней), известные галлюцинации
→ текст пустой: второй заход — весь звук после «Алисы» без вырезок VAD (шёпот, речь издалека)
```

Распознавание на лету (`InterimRecognition`, общее для сессии и `duowave replay`):

```
VAD слышит команду  → раз в 500 мс нового звука: речь, вырезанная VAD → текст в промежуточные
VAD молчит после «Алисы» (guard + 500 мс) → весь звук после «Алисы» → слова есть? это тихая речь:
  тайм-аут «нет речи» снят, текст — в промежуточные, конец — когда текст не менялся 2 с
  (ASR_QUIET_END_MS; пустой результат не считается «не менялся»), финальное — по всему звуку
```

Сессия: `VoiceInput` → `InputStartAck` и промежуточные `AsrResult` раз в 300 мс → пока
человек говорит, фраза распознаётся «на лету» не чаще раза в 500 мс нового звука, и
промежуточные несут этот текст → конец фразы (или колонка закрыла поток сама — распознаём
то, что успели записать) → распознавание (промежуточные идут и во время него) → финальный
`AsrResult` → закрытие потока колонки (если она не закрыла его сама) → `SpotterValidation` →
`AliceResponse`. Отмена, новое «Алиса» или разрыв соединения прерывают запрос молча, вместе с
запросами к распознаванию. Распознавание на лету одно за раз и отменяется финальным.

`SPOTTER_WAIT_MS`: если `SpotterEnd` не пришёл, началом команды служит перезапуск потока Ogg,
а без него — 2,5 с звука (активация не голосом).

## Ответ (этапы 3–4, `src/dialog/`, `src/gateway/yandex/`, `src/gateway/uniproxy/spoken_answer.rs`)

```
текст команды → DialogService: системный промпт (файл перечитывается) + дата и время по
  часовому поясу колонки + история устройства (8 пар, 5 минут)
→ LLM потоком: Claude (Opus 5.5, effort low, server-side fallback) | OpenAI-совместимый | echo
→ PhraseSplitter: первая фраза — как только готово предложение; дальше — предложения от 40
  знаков; разметка убирается
→ каждая фраза сразу в YandexSession: своя сессия uniproxy (заголовки рукопожатия и кадр
  SynchronizeState колонки, открывается ещё пока человек говорит) → TtsGenerate → TtsSpeak +
  Ogg/Opus + закрытие потока
→ SpokenAnswer: звук фраз по порядку → OggOpusJoiner (один serial, OpusHead первой фразы,
  granule подряд, EOS только на последней странице)
→ колонке: AliceResponse, когда первая фраза уже звучит (ждём до 400 мс остаток текста — он
  идёт в ответ и решает should_listen) → TtsSpeak (наш чётный поток) → звук → закрытие потока
```

Новое «Алиса», `CancelRequest`, закрытие колонкой нашего потока или разрыв прерывают ответ:
LLM и синтез отменяются, поток закрывается с `CANCEL`. Модель молчит дольше `LLM_TIMEOUT_MS`
или падает до первой фразы — звучит «Не получилось получить ответ.»; фраза без звука
пропускается; если не озвучилось ничего — `AliceResponse` с одним текстом. `TtsGenerate` от
самой колонки (`alice-say.py`, вокализация) озвучивается так же, без `AliceResponse`.

## Отладка — первый класс

- **Журнал сессии**: `data/sessions/<дата>/<время>_<устройство>_<сессия>/events.jsonl` —
  каждое входящее и исходящее событие с декодированными полями. Идентификаторы устройства и
  аккаунта заменяются хешем (`RECORDER_REDACT`), токены и cookie — всегда, в том числе OAuth-токен
  из заголовков рукопожатия; в protobuf поля токенов не описаны в схеме и не декодируются.
- **Звук запросов**: `audio/<время>_<requestId>.in.ogg` — сырые страницы Ogg от колонки
  (цепочка: буфер с «Алиса», затем команда); `*.asr.wav` — ровно то, что ушло в распознавание;
  `*.asr-all.wav` — весь звук после «Алисы» для второго захода; `*_spotter_*.wav` — звук из
  `LogSpotter`.
- **Таймлайн запроса**: одна строка лога на запрос — от `VoiceInput` до ответа, с отметками
  первого звука, `SpotterEnd`, начала речи, конца фразы, распознавания, ответа, плюс усиление,
  границы речи и текст «как услышан» и «после очистки» (и второго захода, если был). В журнале
  (`voiceTimeline`) — полный отчёт с разметкой VAD по окнам; каждое распознавание на лету —
  событие `interimAsr` с текстом, позицией в звуке и временем.
- **Повтор без колонки**: `duowave replay <file.in.ogg>` прогоняет запись через тот же конвейер
  (`SpeechService`, `InterimRecognition`) с текущими параметрами из окружения — подбор VAD и проверка
  распознавания на реальных записях; `SpotterEnd` берёт из журнала сессии рядом с папкой `audio/`.
- **Неизвестные события**: поля без описания в схеме объявлены как `bytes` и печатаются
  «сырым» разбором protobuf (номер поля, тип, значение), чтобы изучать протокол.
- **Таймлайн ответа**: строка лога и `answerTimeline` в журнале — первая фраза, текст готов,
  первый звук, ответ отправлен, конец звука; число фраз, длительность звука, ошибки. События
  нашей сессии с Яндексом — в том же журнале с направлениями `toYandex` / `fromYandex`.
- **Режим ретрансляции** (`UNIPROXY_MODE=relay`, `relay_session.rs`): сессия колонки уходит в
  Яндекс без изменений, кадры станции, пришедшие до подключения, ждут в очереди; журнал — каждое
  событие с разбором и сырым видом всех полей, звук каждого потока файлом. Так изучаются
  возможности оригинала (шёпот, управление, эмоции) перед тем, как повторять их у себя; выводы
  первых опытов — research/original-alice.md. Токены
  вычищаются: сырой вид `SynchronizeState` не пишется, значения токенов из заголовков и всё
  похожее на OAuth-токен заменяются хешем. Пинги колонки отвечает сам наш сокет, до Яндекса они не
  доходят, поэтому шлюз пингует Яндекс сам (`RELAY_PING_MS`) и обрывает замолчавшее соединение —
  колонка переподключается. Без этого 31.10 соединение умерло после 42 минут тишины и проглотило
  следующий запрос.
- **Отладочный API** (`DEBUG_API_ENABLED`): `GET /debug/sessions`,
  `GET /debug/sessions/:id/events`, `POST /debug/sessions/latest/say` — озвучить текст,
  `POST /debug/sessions/latest/tts` — синтез у Яндекса без звука на колонке (проверка сессии).

## Подводные камни (собраны при разборе колонки и прототипа)

Протокол:
1. Лайт 2 говорит protobuf: бинарные кадры с префиксом `AAPI`. Старые прошивки (~1.56) — JSON
   в текстовых кадрах (пока не поддерживается).
2. Звук — бинарные кадры `[u32 big-endian streamId][страницы Ogg/Opus]`. Потоки колонки
   нечётные, наши — чётные.
3. `VoiceInput` начинается примерно с 2 с буфера, где звучит само «Алиса»; конец ключевого
   слова отмечает `StreamControl.SpotterEnd`. Слово ещё ~300 мс «заходит» за отметку.
4. На колонке `vadEnabled=false`: конец фразы определяет **сервер**. Колонка шлёт звук, пока
   мы не ответим `AsrResult` с `EndOfUtt` и не закроем её поток. Но через ~5 с после
   `VoiceInput` она сама закрывает поток с `NO_SPEECH` и пишет `asr:NoSpeechDetectedError` в
   `RequestStat`, если в промежуточных `AsrResult` не появился текст: без них вообще
   (проверено 30.10.2026) и **с пустыми тоже — даже посреди фразы** (31.10.2026: команда на
   6 с оборвана на 5,0 с, хотя ушло 16 пустых промежуточных). Поэтому промежуточные (раз в
   300 мс до финального, в том числе пока идёт распознавание) несут текст, распознанный на лету:
   с ним колонка слушает, сколько нужно (31.10.2026: 6,2 с речи дослушаны до конца, ответ через
   7,1 с после `VoiceInput`, 11 распознаваний на лету по 100–450 мс). Если колонка всё же
   закрыла поток сама, записанное всё равно распознаётся.
5. На `VoiceInput` сразу отвечаем `InputStartAck`.
6. Причины закрытия потока в protobuf: OK 0, INTERNAL_ERROR 1, STOP_RECORDING 2,
   AUDIO_SOURCE_STOPPED 3, CANCEL 4, NO_SPEECH 5. В JSON-протоколе номера другие.
7. Без `RequestStatAck` колонка повторяет `RequestStat`; на `LogSpotter` ждёт `LogAck`.
8. Новое «Алиса» или `CancelRequest` отменяют текущий ответ. `TtsUpdateState` сообщает,
   сколько ответа успело прозвучать, — по нему обрезать историю диалога.
9. Колонка шлёт `MatchedUser` (кого узнала по голосу; внутри идентификаторы устройства),
   служебные `server_action` (`@@mm_typed_callback`) и проверяет связь `GET /generate_204`
   на нашем хосте — нужен ответ 204.
10. Колонка предлагает сжатие WebSocket zstd (`permessage_deflate_zstd`); отказываемся —
    работает без сжатия.

Звук и речь:
11. После VQE звук тихий (пик около −40 дБ), шёпот ещё тише: усиливать перед распознаванием
    **и перед VAD**, иначе шёпот теряется.
12. Ответ — `AliceResponse` (с директивой `tts_play_placeholder`, канал Dialog — это джингл
    в начале ответа), затем `TtsSpeak` и Ogg/Opus 48 кГц моно в новом чётном потоке, затем
    закрытие потока. Фразы склеиваются в один непрерывный поток.
13. `should_listen` в ответе — колонка слушает без «Алиса» сразу после ответа.
14. Быстрые команды (громкость, пауза, следующий трек, блютуз) колонка может выполнить сама,
    не обращаясь к серверу.

Интеграции:
15. Claude и GPT-5 отклоняют `temperature` ниже 1 — не отправлять.
16. В JS (Node-шлюз, пульт) `\w` не ловит кириллицу — в регулярках `\p{L}` с флагом `u`. В Rust крейт
    `regex` понимает Юникод сам, но не умеет look-around — такие шаблоны переписываются кодом.
17. API шлюза оборачивает ответы в `{message, code}` (`ok(…)`, `ApiError` в `src/platform/http/api.rs`,
    как прежний `TransformInterceptor` Nest) — маршруты для колонки (её HTTP, `/media`, страница звонка,
    скрипты колонки) отдают ровно свой формат, без обёртки.
18. Прямые ссылки Яндекс Музыки отдаются через 308 — плеер старой прошивки их не проходит,
    конечный адрес находить на сервере.
19. Часовой пояс брать из `Application.Timezone` колонки, а не из конфига.

Звук колонки (по записям с Лайт 2, этап 2):
20. После `SpotterEnd` колонка начинает **новую цепочку Ogg с тем же serial**: новая страница
    BOS с `OpusHead`, у первой цепочки нет EOS. Демультиплексор узнаёт цепочку по `OpusHead`,
    а не по смене serial. `ffprobe` и плееры показывают длительность только последней цепочки.
21. Буфер ключевого слова — ровно 2,00 с (100 пакетов по 20 мс), приходит пачкой за ~10 мс до
    `SpotterEnd`; ещё ~0,4 с после него — тоже пачкой, дальше реальное время. Opus — SILK WB
    16 кГц, 20 мс, пакет на страницу. Речь после VQE: окна 32 мс до −50 дБ, тишина −78…−81 дБ.
22. `VoiceInput` несёт `activation_type` (`spotter`) и `spotter_phrase` (`алиса`): по ним видно,
    будет ли буфер с ключевым словом и что убирать из текста.
23. Распознавать с начала «Алисы», а не с `SpotterEnd`: команду, сказанную без паузы, иначе
    режет посреди первого слова. Начало «Алисы» находится по разметке VAD назад от отметки;
    само слово потом убирается из текста.
24. Решения VAD — по времени звука, не по часам: пачки буфера не сбивают таймеры, а запись
    повторяется один в один (`duowave replay` и тесты конвейера).
25. `LogSpotter` приходит отдельным соединением: событие с `header.stream_id`, затем сырой PCM
    (`format: audio/x-pcm;bit=16;rate=16000;channels=1`), закрытие потока OK — и соединение
    рвётся с кодом 1006. Это нормально.
26. Silero работает на ONNX Runtime — готовой библиотеке, которая скачивается при сборке с `--features silero`
    и в статическую сборку musl не входит. Поэтому образ Docker (Alpine) и дополнение HA слышат конец фразы по
    энергии (`VAD_ENGINE=energy`); без `silero` в сборке `VAD_ENGINE=silero` тоже уступает энергии. (В
    Node-шлюзе onnxruntime-node не работал на musl, и образы были на Debian slim.)

Ответ и голос (этапы 3–4, по коду Quasar Bridge и прошивке; живая проверка — впереди):
32. В заголовках рукопожатия колонка шлёт OAuth-токен (`x-uprx-oauth-token`) и uid аккаунта
    (`x-uprx-uid`). Журнал хеширует токены и cookie всегда, идентификаторы — при
    `RECORDER_REDACT`. До 31.10.2026 токен писался в журнал открытым текстом: исправлено, старые
    журналы вычищены.
33. Голос Алисы есть только в облаке Яндекса: синтезатора на колонке нет, лишь готовые фразы в
    `/system/vendor/quasar/sounds/ru-RU/`. Сессию для синтеза открывают учётные данные колонки:
    те же заголовки рукопожатия и её исходный кадр `SynchronizeState` (токены в нём не описаны в
    нашей схеме, поэтому он уходит байт в байт). Запрос — `TtsGenerate` (текст, `ru-RU`,
    `audio/opus`, без `voice` — голос сессии, то есть Алиса); ответ — `TtsSpeak` с
    `refMessageId` нашего `TtsGenerate` и своим номером потока, звук, `StreamControl` close.
    Сессию только для синтеза Яндекс принимает (проверено 31.10.2026 без звука на колонке,
    `POST /debug/sessions/latest/tts`): подключение с TLS ~1,9 с и `SynchronizeState` ~0,3 с,
    поэтому сессия открывается, пока человек ещё говорит; первый звук через ~0,4 с после
    `TtsGenerate`, секунда речи приходит за ~20 мс. После `SynchronizeStateResponse` Яндекс шлёт
    push «notify» (поле 5 события, в схеме не описано), `TtsSpeak` пришёл на чётном потоке 4.
34. Колонка заканчивает проигрывание на странице Ogg с EOS так же, как на закрытии потока:
    фразы склеиваются в один поток, EOS — только на последней странице.
35. `TtsSpeak` колонке ссылается на её запрос (`VoiceInput` / `TextInput`), поток — наш чётный;
    `AliceResponse` уходит до `TtsSpeak`.
36. Ответ колонка ждёт ~15 с (тайм-аут VINS по наблюдениям Quasar Bridge): до первой фразы
    модели — `LLM_TIMEOUT_MS` (10 с), до звука фразы — `TTS_TIMEOUT_MS` (5 с).
37. Claude Opus 5.5 не выключает рассуждение: скорость ответа задаёт `effort` (`low`);
    `temperature` не отправляется (пункт 15).
38. `alice-say.py` и вокализация через glagol приходят к нам как `TtsGenerate`: `uniProxyUrl`
    указывает на шлюз, и колонка просит синтез у него.

Связь с колонкой (08.11.2026, по живому сокету и журналам; разбор — plans/station-liveness.md):
39. В простое колонка не шлёт ни одного кадра (37 минут подряд в журнале), только пустой WebSocket ping
    каждые 5 с (6 байт; наш сокет отвечает pong, 2 байта: 90 из 90 за 450 с). Перезагружаясь или
    теряя сеть, она не шлёт ни FIN, ни RST: сокет на Mac остаётся ESTABLISHED, а сессия
    «подключённой», пока шлюз сам в неё не запишет (08.11 — 21 минуту, до пуша Яндекса; 06.11 —
    38 минут, до смены режима). Поэтому шлюз пингует колонку сам (`STATION_PING_MS`, 15 с) и
    обрывает сокет с 1006, если от неё не пришло ничего — ни кадра, ни её пинга, ни понга — за три
    пинга (45 с). Запись в перезагрузившуюся колонку возвращается сбросом сразу (08.11 пуш Яндекса —
    через 6–10 мс), так что после перезагрузки сокет уходит с первым же нашим пингом, как только
    колонка снова в сети. В ретрансляции так же: наши пинги Яндексу и его пинги нам до колонки не
    доходят.
40. Сокет, закрытый штатно (смена режима, её собственное закрытие), колонка открывает снова не
    сразу: через 1 с – 2,5 мин (медиана около минуты, 23 раза за 06–08.11), а со словом «Алиса» —
    тут же. Пока его нет, присутствие — «переподключается» (три минуты, как после перезапуска
    шлюза), а не «не в сети». Сокет, оборванный без закрытия (1006: сброс, тишина), — «не в сети»
    сразу: колонка может быть выключена.

## Этапы

1. **Протокол и наблюдаемость** (готово): ws-сервер, AAPI-кодек, сессии, журнал, запись
   звука, таймлайн, отладочный API.
2. **Звук и распознавание** (готово): Ogg/Opus → PCM, усиление по «Алисе», Silero VAD, конец
   фразы, промежуточные `AsrResult` с текстом на лету, ASR через OpenAI-совместимый сервис
   (GigaAM в `asr-server/` или облако), тихая речь (шёпот) без VAD, повтор записей.
3. **Диалог** (готово): LLM (Claude, OpenAI-совместимый, echo) со стримингом по фразам,
   системный промпт из файла, время колонки, история по устройству.
4. **Синтез и ответ** (готово, проверено вживую 31.10.2026 в режиме echo: ответ голосом Алисы
   колонка доиграла до конца, звук через ~0,9 с после финального текста): поток ответа колонке,
   `should_listen`, отмена; озвучка голосом Алисы через нашу сессию с Яндексом, `TtsGenerate`
   от колонки. Свой синтез — позже.
5. **Сеть**: колонка ходит в Яндекс только через наш сервер — план.
6. **Возможности Алисы** (реализовано 01.11.2026, ждёт живых проверок —
   список): этапы 0–8 и 10 плана интеграции:
